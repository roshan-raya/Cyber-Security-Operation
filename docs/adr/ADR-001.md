# ADR-001: Use Ansible for patch orchestration

**Date:** 2024-02-26
**Status:** Accepted
**Deciders:** Catnip Games DevOps team

---

## Context

Catnip Games needs to patch approximately 300 Linux servers across two data centres
on a regular cadence. Recent incidents during beta testing showed that manual and
inconsistent patching caused version mismatches between game servers, leading to
player disconnections. An automated, repeatable solution is required.

Candidates evaluated:
- Ansible
- Chef
- Puppet
- Custom shell scripts

---

## Decision

We use **Ansible** for patch orchestration.

---

## Reasons

**Agentless architecture:** Ansible requires only SSH access to target hosts.
Chef and Puppet require agents installed and maintained on every server. With 300
servers across two data centres, agent lifecycle management adds significant
operational overhead and becomes a failure point of its own.

**Idempotency by design:** Ansible modules are idempotent — running the same
playbook twice produces the same result. Shell scripts require manual idempotency
checks and are error-prone. This is critical for patch management where a partial
run (due to network interruption or reboot) must be safely re-run.

**YAML playbooks are readable:** Non-specialists can read and audit Ansible
playbooks. Chef and Puppet use Ruby DSLs with steeper learning curves. For a
startup team, maintainability matters more than raw power.

**Role-based structure:** Ansible's role system (common, health_check, patch,
reporting, security_scan) maps naturally to our patch lifecycle stages and allows
each role to be tested and developed independently.

**Industry adoption:** Ansible is the most widely adopted configuration management
tool for Linux patching. Skills are transferable; hiring is easier.

---

## Alternatives rejected

**Chef:** Powerful but requires agents on all targets and has a steeper learning
curve. Ruby DSL is less readable for audit purposes.

**Puppet:** Similar agent requirement to Chef. Declarative model is well-suited to
configuration management but adds complexity for one-time patch operations.

**Shell scripts:** Fast to write but not idempotent, hard to test, and difficult to
extend with reporting, rollback, and monitoring hooks. Fine for simple tasks;
insufficient for 300 servers with compliance requirements.

---

## Consequences

**Positive:**
- No agents to maintain on target hosts
- Playbooks are readable and auditable
- Idempotent runs are safe to retry
- Role structure supports test-driven development with Molecule

**Negative:**
- SSH-based approach has higher latency than agent-based tools at scale
- Ansible is not a full configuration management system — drift detection requires
  additional tooling (handled by drift_check.yml)
- Parallel execution via strategy: free works for 5 test nodes but requires tuning
  (forks, serial, max_fail_percentage) for 300 production nodes

**What is implemented in this repository:**
- This ADR is implemented as a Docker Compose simulation with 5 patch targets for
  coursework development and demonstration. The decision rationale still maps to
  the intended 300-server operational scenario.
