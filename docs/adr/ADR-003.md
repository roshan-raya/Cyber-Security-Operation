# ADR-003: Use Prometheus and Grafana over hosted monitoring

**Date:** 2024-02-26
**Status:** Accepted
**Deciders:** Catnip Games DevOps team

---

## Context

The patch management system needs monitoring and alerting that can:
- Track patch compliance percentage over time
- Alert when compliance drops below 95%
- Show per-host patch status and duration
- Integrate with custom metrics from the Ansible patch runs
- Work without external dependencies during development and demo

Candidates evaluated:
- Prometheus + Grafana (self-hosted)
- Datadog
- New Relic
- AWS CloudWatch

---

## Decision

We will use **Prometheus and Grafana** (self-hosted via Docker) for metrics,
dashboards, and alerting, with **Alertmanager** for alert routing.

---

## Reasons

**Custom metric schemas:** Our patch compliance metrics
(patch_compliance_percentage, patch_host_success, patch_run_duration_seconds)
are custom business metrics that do not exist in any hosted monitoring product's
default integration. With Prometheus, we define exactly the metrics we need via
the patch_metrics_exporter.py and patch_metrics.prom.j2 template. In Datadog or
New Relic, custom metrics require additional configuration and incur cost.

**No external dependency:** Prometheus and Grafana run inside our Docker Compose
stack. The entire monitoring system works offline and in CI without any API keys,
accounts, or network access to external services. This is essential for a demo
environment that must work reliably anywhere.

**Cost:** Datadog and New Relic charge per host per month. For a 300-server
environment, costs would be significant. Prometheus is free and open source.

**Alertmanager integration:** Prometheus includes Alertmanager for alert routing,
which supports webhook receivers, Slack, PagerDuty, and email out of the box.
Our severity-based routing (critical → webhook, warning → console) is configured
in a single YAML file.

**Grafana dashboard as code:** Our patch-slo.json dashboard is version-controlled
alongside the codebase and provisioned automatically on startup. Dashboard-as-code
means the monitoring setup is reproducible. Hosted tools often store dashboards in
their own systems, making them harder to version-control and reproduce.

**Industry standard:** Prometheus + Grafana is the de facto standard for Kubernetes
and cloud-native monitoring. Skills are highly transferable.

---

## Alternatives rejected

**Datadog:** Excellent product but costs money per host, requires internet access,
stores data externally, and custom metrics require additional agent configuration.
Inappropriate for a development environment.

**New Relic:** Similar concerns to Datadog regarding cost and external dependency.
Free tier is limited and would not support 300 hosts.

**AWS CloudWatch:** Tightly coupled to AWS. Our test environment runs locally in
Docker, not on EC2. CloudWatch requires AWS credentials and has costs per metric
and alarm.

---

## Consequences

**Positive:**
- Full control over metric schemas and retention
- No external dependencies or costs
- Dashboard and alert rules are version-controlled
- Works offline and in CI
- Alertmanager provides flexible routing with inhibition rules

**Negative:**
- We own the infrastructure — Prometheus TSDB storage management,
  retention policies, and HA are our responsibility in production
- No built-in anomaly detection (Datadog/New Relic have ML-based alerting)
- Grafana UI changes are not automatically version-controlled unless exported
  to JSON and committed (we handle this via provisioning)

**Implementation scope in this repository:**
- This ADR is implemented as a self-hosted monitoring stack in Docker Compose
  (Prometheus, Grafana, Alertmanager) for the 5-node simulation, while preserving
  metric and alert design that maps to the larger coursework scenario.
