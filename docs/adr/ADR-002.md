# ADR-002: Use Docker Compose for the test environment

**Date:** 2024-02-26
**Status:** Accepted
**Deciders:** Catnip Games DevOps team

---

## Context

The patch management system needs a test environment that:
- Closely simulates real Linux servers with SSH, apt, and systemd-like services
- Can be spun up by any engineer in under 5 minutes
- Is reproducible across macOS, Linux, and CI environments
- Does not require cloud infrastructure or provisioned VMs
- Can simulate multiple data centres and host groups

Candidates evaluated:
- Docker Compose with custom containers
- Vagrant with VirtualBox VMs
- AWS EC2 instances
- Local bare-metal servers

---

## Decision

We use **Docker Compose** with custom Ubuntu-based containers as the test
environment for development and demonstration.

---

## Reasons

**Reproducibility:** `docker compose --profile sim up -d` gives any engineer an
identical 5-node environment in under 2 minutes regardless of host OS. Vagrant
requires VirtualBox which has macOS compatibility issues. EC2 requires AWS credentials
and costs money to run continuously.

**Lightweight:** Docker containers start in seconds. VMs take 1-3 minutes and consume
significantly more RAM and CPU. On a developer laptop running an IDE, monitoring
stack, and 5+ VMs simultaneously is impractical.

**CI compatibility:** GitHub Actions runners have Docker pre-installed. Running the
full test suite in CI with docker compose --profile sim is straightforward. Vagrant
cannot run in GitHub Actions without nested virtualisation. EC2 requires AWS credentials
in CI secrets and adds cost per CI run.

**Custom Dockerfiles:** Our ansible/target/Dockerfile builds a container that runs
SSH, apt, and basic system services — close enough to a real Ubuntu server for patch
testing. It is maintained in the repository alongside the playbooks.

**Profile-based composition:** Docker Compose profiles (--profile sim) let us run
the monitoring stack independently of the patch simulation. This means developers
can work on Grafana dashboards without starting 5 patch targets.

---

## Alternatives rejected

**Vagrant + VirtualBox:** Better VM fidelity but too slow to start, macOS/Apple
Silicon compatibility issues, cannot run in GitHub Actions CI.

**AWS EC2:** Highest fidelity but requires cloud credentials, costs money, and has
non-trivial setup time. Inappropriate for a development environment that needs to
start and stop frequently.

**Local bare-metal:** Not reproducible across team members. State accumulates between
test runs. Cannot be automated in CI.

---

## Consequences

**Positive:**
- Any engineer can run `make up-sim` and have a full environment in 2 minutes
- CI uses the same environment as local development
- No cloud cost or credentials required
- Environment is version-controlled alongside the code

**Negative:**
- Docker containers are not full VMs — some system-level behaviours differ
  (e.g. systemd not running by default, kernel is shared with host)
- Reboot testing requires workarounds (containers restart rather than reboot)
- Network simulation (e.g. packet loss, latency) requires additional tooling

**What is implemented in this repository:**
- This ADR is implemented with Docker Compose `--profile sim`, using one Ansible
  control node and five simulated Linux patch targets for reproducible team and CI
  execution.
